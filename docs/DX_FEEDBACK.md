# Ledger developer experience feedback

Evidence collection starts after physical hardware is available. Each entry will include observed behavior, expected behavior, suggested fix, and a source URL.

## Current observations

- `wallet-cli` 2.1.0 exposes Key Ring initialization only through a device-required `ring init`; the CLI has no explicit enrollment/export/import command for a second host.
- The exact cross-host recovery path is not safe to infer without testing the Ledger Sync/LKRP user flow.
- Hiero SDK's `PrivateKey.fromString()` is deprecated in favor of `fromStringECDSA()`/`fromStringDer()` and prints a runtime warning on every call, but this is easy to miss: nothing in the type signature flags it, and the deprecated path still works correctly (verified: a raw viem-generated hex ECDSA key round-trips identically through both — same `toStringRaw()`, same derived EVM address). A judge or newcomer following an older example (this repo's own Day 2 code did) would carry the warning into every subsequent run without knowing there's a non-deprecated equivalent that behaves identically.
- **`@earendil-works/pi-coding-agent` 0.85.1's extension loader (jiti) fails to load any extension with a *static* top-level import of `@ledgerhq/device-signer-kit-ethereum` anywhere in its module graph**, with `Error: Failed to load extension "<path>": Failed to load extension: Cannot redefine property: module.exports`. Reproduced by bisecting imports one at a time in a minimal extension against the real installed `pi` CLI: `@ledgerhq/device-management-kit` alone loads fine, `@ledgerhq/device-transport-kit-node-hid` alone loads fine, adding `@ledgerhq/device-signer-kit-ethereum` breaks it every time, regardless of what else is imported alongside it. A dynamic `import("@ledgerhq/device-signer-kit-ethereum")` inside the function that needs it avoids the failure entirely — the package works correctly once loaded, so this looks like a jiti-side module-transform issue with that specific package's build output (likely a double `Object.defineProperty(module, "exports", ...)` from its bundler colliding with jiti's own interop wrapper), not a real API incompatibility. This is exactly the kind of failure a Ledger-integrating Pi extension author would hit immediately and have no obvious path to diagnosing — worth a) an issue against `@earendil-works/pi-coding-agent` or jiti, and b) a note in Ledger's own DMK docs recommending dynamic imports for Pi/jiti-hosted extensions until it's fixed upstream.
- `@hashgraphonline/standards-sdk@0.1.186`'s published `dist/es/index.d.ts` does not surface `canonicalizeAgentData`/`createUaid`/`CanonicalAgentData` through its `export *` re-export chain under TypeScript's `nodenext` module resolution, even though both functions run correctly at runtime (verified directly, deterministic UAID generation confirmed). `hcs-14/sdk.d.ts` imports `Client` from a relative path (`../../node_modules/@hashgraph/sdk`) that does not exist in the published package, which appears to be what breaks the barrel re-export for TypeScript specifically (runtime ESM resolution is unaffected). Consumers hit `TS2305: has no exported member` on functions that demonstrably exist and work; the fix (published here as `docs/DECISIONS.md` ADR-009) is a manual type assertion documenting the real shape, since importing by name doesn't type-check.

- `@ledgerhq/device-management-kit@1.9.0`'s ESM entrypoint fails under native Node 22 because it imports the `./src` directory without a file extension: `ERR_UNSUPPORTED_DIR_IMPORT`. The package's CommonJS entrypoint loads and exposes the same API. A Node application using the published ESM default can therefore fail at the first real Ledger mandate operation even though the package installs and typechecks; the workaround in Finity is lazy CommonJS loading via `createRequire(import.meta.url)`. Ledger's package should publish Node-compatible ESM specifiers or document the CommonJS entrypoint for native Node consumers.

- A physical run reached Ledger signature completion, then finityd returned only `invalid_request`. The daemon's outer request guard was masking registration exceptions from the contract relay and HCS trace setup, making diagnosis impossible. Finity now verifies the signature locally against the Ledger-derived address before relay and returns only safe registration categories. Ledger-integrating applications should expose a typed, redacted failure stage at this boundary instead of a generic HTTP request error.

- After that fix was built, `pnpm agent` still reused a healthy finityd started before the rebuild because its liveness check did not validate the runtime version. This made a correct code change appear ineffective. Finity now treats a version-mismatched daemon as stale and starts the current runtime; developer tooling should pair health checks with an explicit build or protocol version.

- The command-center `/finity mandate new` path then returned `registration_failed` because it had bypassed the local Ledger signature/address check, while the daemon's generic fallback hid the failing live stage. Finity now applies the same verification to that command and returns redacted contract, receipt, status, HCS-topic, or trace-binding categories.
- A retry after revoking a mandate still failed at contract submission because the editable `mandate-draft.json` retained nonce `"1"`. The registry intentionally consumes a principal nonce permanently, so the error was correct but the draft workflow was misleading. New mandate commands now refresh only the registration nonce immediately before compilation and Ledger clear signing; the visible policy choices remain stable and a retry is actionable.
- The control-center setup action stopped after generating a broker alias and required a manual HBAR transfer plus mirror-node account-ID copy/paste. This was especially confusing because the same package already had a tested Ledger transaction signer. Setup now detects reusable state, derives the funding amount from the public mandate draft, requests the transfer from the Ledger with an explicit summary, and resolves the Hedera account automatically.
